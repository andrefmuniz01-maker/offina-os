# Mapeamento de compatibilidade MySQL → Supabase PostgreSQL

## Escopo e preservação

A origem MySQL permanece ativa e não será apagada durante a migração. O inventário atual contém 37 registros em `users` e nenhuma linha de negócio em tenants, clientes, estoque, orçamento, OS, financeiro ou anexos. Portanto, esta primeira migration estabelece apenas a fundação PostgreSQL; a migração de dados históricos exigirá reconciliação por contagem e por chave de origem quando houver dados de produção disponíveis.

| Origem MySQL | Destino Supabase | Estratégia |
|---|---|---|
| `users.id` inteiro e `openId` | `auth.users.id` UUID + `public.profiles.id` UUID | Supabase Auth é a identidade oficial; manter chave de origem em etapa de carga histórica quando necessário. |
| `users.platformRole` | `profiles.platform_role` | Papel global persiste somente em tabela protegida e não pode ser alterado pelo próprio usuário. |
| `tenant_members.userId` | `tenant_members.user_id` UUID | O membership continuará sendo a fonte de pertencimento ao tenant. |
| IDs inteiros de domínio | `bigint generated by default as identity` | Preserva semântica relacional e reduz risco de conversão de FKs de negócio. |
| JSON MySQL | `jsonb` | Endereços, permissões, respostas, eventos e metadados passam a `jsonb`. |
| Forge/S3 `storageKey` | `storage.objects` em bucket privado + `attachments.storage_key` | O arquivo será isolado pelo primeiro segmento do caminho, equivalente ao `tenant_id`. |

## Regras de corte

1. Nenhum dado é removido da origem MySQL.
2. Supabase Auth cria UUIDs; nunca se fabrica uma identidade OAuth para usuário existente.
3. A carga de usuários deve ocorrer por fluxo de convite/login do Supabase Auth ou por rotina administrativa com mapa de IDs auditável.
4. A aplicação só troca a leitura/escrita para Supabase depois que as contagens, FKs, RLS e os testes Tenant A × Tenant B forem aprovados.
